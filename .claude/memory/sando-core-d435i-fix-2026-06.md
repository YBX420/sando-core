2026-06-25: diagnosed why the certified go-around (`render_3d_video.py --ego --maneuver --d435i`) FAILED to plan / didn't reach, and tuned it to GT-similar. On the canonical demo **seed 3**: was reached=False/many optimise failures → now **reached=True t_goal=13.2s, collided=False, min_clr=0.527m** vs GT-perception reference **11.1s / 0.421m**. D435i ~2s slower (honest cost of 8 m occluded depth vs GT's 14 m see-through cone), clearance comparable/better.

**Four independent root causes, all fixed (none was the algorithm):**

1. **`perceive()` restores the camera pose before returning → deprojection used WRONG extrinsics.** `metaurban/.../base_camera.py:perceive()` reparents+setPos+setHpr, renders, then RESTORES the camera to its original pose (lines 201-205). `D435iDepth.cloud_world` read `self.cam.cam.getNetTransform()` AFTER `capture()` returned → got the restored (constant) pose, so the world cloud always landed in a FIXED orientation (≈world +X) regardless of requested heading. Probe `metaurban/d435i_probe.py` proved it: cloud_mean_bearing stuck at ~0° for every requested heading. **Fix:** in `d435i_sensor.cloud_world`, build the cam→world matrix from the INPUTS — `parent_node.getNetTransform().compose(TransformState.makePosHpr(position, hpr))` — not from the restored camera node. After fix cloud_mean_bearing tracks heading 1:1, frac_in_cone=1.0. This was a latent bug in the whole D435i integration (the old drone.origin mount only "worked" because the route heading happened to sit near the camera's constant restored aim).

2. **Depth cam was bolted to body yaw, not travel heading.** `d435i_cloud` mounted on `drone.origin` (= `quad.yaw` via set_heading_theta). In a go-around the body yaw swings off the goal direction during climb/turn → camera stared backward (frac_ahead→0) → EGO planned against a behind-the-drone cloud → more failures → more climb → divergent loop. GT `fov_cloud` is aimed along the GOAL `heading`; D435i wasn't. **Fix:** `d435i_cloud(p_d, heading)` now mounts world-frame aimed along `heading` (h = deg(heading) + FPV_HPR[0]); both call sites (native --ego line ~1080, `_man_cloud` line ~708) pass their heading. (Real drones yaw perception toward travel — legitimate.)

3. **Maneuver replanned to the raw 75 m goal, not the receding horizon.** `ego_maneuver_replan` computed `L=min(EGO_HOR,dist)` + `gdir` but REPLANNED straight to `cur_wp` (far goal). With 8 m depth range that goal is far outside perception → EGO extrapolates into unmapped space → optimise fails → climb. Native --ego clips to EGO_HOR (=12) and so hits 94/94. **Fix:** maneuver now replans to the clipped local goal `p_d[:2] + gdir*L`. (Shared code — verified GT maneuver still reaches.)

4. **Dense depth cloud (~4000 pts) timed out EGO's A* front-end (0.2 s budget) → "a star error".** GT fov_cloud is a few-hundred coarse voxels; raw D435i depth is ~4000 dense surface points, and the maneuver tries straight/over/climb (3 A* per tick) → constant timeouts → erratic altitude (dove to 0.1 m), no progress. **Fix:** voxel-downsample `d435i_cloud` to ~1 pt / `D435I_VOX`(=0.25) m cell → n≈677 → astar_fail 133→0, ok0 133→29. Also: with d435i the depth already paints the mover's CURRENT surface, so `_man_cloud` now feeds ONLY the predicted (t_cpa) keep-out ring for movers (skip the lead=0 ring) — avoids double-inflating the current position and sealing the corridor; current-position d_safe is still enforced by `cert_clear()`. This took static clearance 0.03 m → 1.0 m.

**Multi-seed A/B (ours --maneuver, GT vs --d435i, `metaurban/d435i_ab.sh`):** seed3 GT 11.1s/clr0.42 vs d435i 13.2s/clr0.33 BOTH 0-collision ✓. seed5 GT reach 11.4s/clr0.04(near-miss) vs d435i reach 13.1s but static **-0.30 collide**. seed1 GT fail+collide(astar 3392) / d435i safe but no-reach. seed9 GT fail+collide static-0.69 / d435i no-reach. **Takeaway: the maneuver FRONT-END's static safety is fragile on hard seeds for BOTH GT and D435i** (cert only guards movers; static rides on EGO's own avoidance which cuts to ~0). So "GT-similar" is clean on seed3; on seed5 D435i is slightly worse than GT's own near-miss; this is a shared maneuver-planner static gap, not a D435i planning failure.

**Occupancy memory (OCC_MEM=1, opt-in, currently OFF):** d435i collides static because depth only sees an obstacle's FRONT and clips its unseen side/back after passing. The principled fix is a world-frame static memory (`occ_remember`/`occ_reset`). The NAIVE version REGRESSED (seed5: froze, climb×31, collide -0.86) because mover surfaces removed only at the current frame leave phantom walls along mover trails + the 22 m accumulation over-densifies → walls the drone in. Left in, gated OFF by default; fixing needs decay + mover-track removal. Future.
